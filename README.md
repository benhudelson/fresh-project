# Fresh Project Setup

Captures a project-management and documentation pattern so a new project can adopt the same structure without copying scaffolding files. Update this document when the pattern evolves; rebuild from the updated document on the next project.

This is **instructions, not scaffolding** — read it, then build the files. When the pattern shifts, edit this doc and rebuild on the next adoption.

---

## The pattern in one paragraph

Three forcing functions: (1) tight functional scope discipline paired with rigorous technical quality, (2) tiered documentation that respects a downstream context budget, and (3) explicit hierarchy (Phase / Feature / Task group) coupled to Linear for status while keeping the repo as the source of truth for *what*. The agent-role split (lead PM + eval-author + engineering + quality) is what makes the artifact split (`requirements.md` / `plan.md` / `validation.md` / `evals/`) load-bearing. Everything below makes those work.

---

## Mental model: the PM role

The lead agent (the one in conversation with the user) is the **project manager**. Two governing concerns shape every interaction:

1. **Tight scope discipline (functional).** Smallest shippable unit. Do **not** surface edge cases, alternatives, or "while we're at it" extensions. Push back on scope creep — including the agent's own. **Capture, don't expand**: out-of-scope refinements go to the polish backlog (below), not into the active spec.

2. **High technical quality.** Rigorous on correctness, architecture, testability, security, performance, maintainability. Raise edge cases freely here.

**Mode switch.** If unsure which mode applies, ask: is this a functional question or a technical one? Functional → stay tight. Technical → be rigorous.

## Persistence policy

- **`CLAUDE.md`** — perpetual guidance; principles, conventions, rules that govern indefinitely.
- **Memory** (`~/.claude/projects/<sanitized-project-path>/memory/`) — items that will eventually close out: in-flight state, deadlines, pending decisions awaiting formalization.

**Test before saving:** "Will this ever be closed out?" No → `CLAUDE.md`. Yes → memory.

**Memory hygiene.** Update or remove memory the same turn an item changes state. When an item fully closes, *delete* the entry — do not leave "done" or "resolved" markers; closed entries accumulate and obscure what is actually open. Cite the commit SHA / Linear ID / ADR slug for the state change in the conversation reply, not in the memory entry. If a change invalidates a kickoff prompt's "what landed" or "open work" sections, flag to the user rather than silently editing the kickoff — kickoffs are historical artifacts; memory is the live view.

**Do not save to memory:** code patterns derivable from current project state; git history / who-changed-what; debugging fix recipes; anything already in `CLAUDE.md`; ephemeral task or conversation state.

## File scaffolding at project init

```
project-root/
├── CLAUDE.md                    # root invariants — always loaded
├── .claude/skills/              # vendored utility skills (git subtree) — see § Skills
└── docs/
    ├── CLAUDE.md                # path-scoped invariants for docs/
    ├── canonical-sources.md     # registry of recurring facts
    ├── polish-backlog.md        # out-of-scope capture
    ├── roadmap.md               # phase ordering + per-phase exit criteria
    └── decisions/               # ADRs as YYYY-MM-DD-<slug>.md
```

Add as they come online:

- `docs/research/` — research reports. `status: live | frozen-reference` frontmatter required. Freeze rather than delete — the audit trail matters.
- `docs/architecture/` — architecture overviews (e.g. data models, frameworks that span multiple specs, NFR canonical doc).
- `docs/operations/` — recording artifacts created during execution: provisioning ledgers, rollback runbooks, restore drills, per-incident files. Records what *happened*, not what was *decided* (decisions go to ADRs). Path-scoped `CLAUDE.md` enforces the recording-not-deciding rule. See § Operations directory below.
- `docs/kickoff-prompts/` — session handoff prompts (generated by the handoff-kickoff skill — see § Skills).
- `specs/YYYY-MM-DD-feature-name/` — feature specs. Required contents below. A path-scoped `specs/CLAUDE.md` carries the directory-shape, NFR-gate, and ENG-N-additive-only invariants.
- `apps/`, `apps/<app>/components/`, etc. — each top-level directory gets its own path-scoped `CLAUDE.md` when invariants distinct from the root accumulate.

## Root `CLAUDE.md` shape

Terse — this file is always loaded into every conversation, so it counts against the context budget for every task. Depth lives in ADRs and architecture docs that are loaded on demand.

Sections, in order:

1. **My role** — PM role described above; the two governing concerns and the mode switch.
2. **Tight scope discipline** — explicit do/don'ts plus the "Capture, don't expand" rule pointing at `docs/polish-backlog.md`.
3. **High technical quality** — concerns enumerated.
4. **Persistence policy** — `CLAUDE.md` vs memory; the "will this ever close out?" test.
5. **Context discipline** — subsections:
   - **Canonical sources** — pointer at `docs/canonical-sources.md` and the "write a pointer, not a copy" rule.
   - **Context budget** — ≤7,000 tokens (cl100k_base) for file-content reads on downstream tasks; tiered docs pattern.
   - **ADRs** — location, immediacy, fixed shape.
   - **Spec-driven pipeline** — no implementation without a spec in `specs/`. **NFR gate**: every spec's `validation.md` enumerates applicable NFR rows from the canonical NFR doc — pointer, not restatement — and states how each is verified. Skipped rows are reasoned. A spec with no NFR section does not pass review.
   - **Branch and PR workflow** — one long-lived branch per *phase*, named `phase-<n>-<kebab-phase-slug>`. Engineering commits land on it (one commit per task-group Issue); a single PR opens into `main` at phase completion. Phase-independent work (ADRs, kickoff prompts, `CLAUDE.md`, governance) commits to `main` directly. See § Roadmap and workflow hierarchy → Branching. **Automated PR review (opt-in; requires setup — do not assume it is preconfigured):** once a PR-review bot is wired up for the repo, every PR gets an automated review and the opening agent triages each finding on the PR — fix / rebut with a spec-or-ADR citation / escalate to the user — before handing the PR over; valid-but-out-of-scope suggestions go to `docs/polish-backlog.md`, not the PR.
   - **Linear references** — `<ID> (<Title>)` on first mention in every human-readable surface.
   - **Attribution ban** — no `Co-Authored-By`, no "Generated by Claude" footers, scrub on contact.
   - **Handoff path** — two directives: `handoff-path: <relative-path>` and `handoff-file: <filename>` (e.g., `handoff-path: docs/kickoff-prompts/` + `handoff-file: next-session-kickoff.md`). The handoff-kickoff and resume skills grep for both; explicit values beat the skills' default-resolution fallback and lock the convention against drift. A single canonical kickoff file is overwritten each regen (no dated names, no `-vN`) — git history is the audit trail. Kickoffs commit to `main`; from a phase branch, read the latest via `git show main:<handoff-path>/<handoff-file>` — never copy it into the phase branch's tree.
   - **Handoff narrative routing** — the kickoff carries no inline tables for verification debt or parked/waiting-on-human items; those live in memory (`project_verification_debt.md`, `project_pending_decisions.md`) and the kickoff emits one-line pointers. Both pass the persistence test (each entry eventually closes out).
   - **Handoff regen cadence** — kickoffs regenerate at session boundary only (user-signaled, or agent-proposed under context-budget pressure). Mid-session state changes update memory and are flagged in chat; they do **not** trigger a regen.
6. **Agent operating notes** — runtime quirks of the harness that aren't principles but bite if ignored. Examples: Bash working directory persists between calls, so prefixing every command with `cd <project-root> && …` is redundant and forces user-specific compound permission allowlists; never chain commands with `&&` / `;` when each individual command is already allowed by a permission rule (chaining triggers prompts that bare commands don't); prefer CLI over UI for config/provisioning/operational actions, delegating to a browser dashboard only when no CLI path exists or interactive auth can't be scripted; when a vendor CLI lacks an operation, fall back to the vendor's API directly and reference API tokens via environment variables (never paste literal secrets into commands). Standing cross-project principles to encode here too: **tables over prose** — whenever output has parallel structure (steps, results, option comparisons, status matrices) present one markdown table, not prose or a stacked list; the `step-table` skill is the formatting authority. **Hand the user runnable commands, not prose directions** — any action the user runs themselves ships as an exact copy-pasteable command (or a precise dashboard click-path when no CLI exists), never a description they must reconstruct. **Prefer in-conversation table prompts over the `AskUserQuestion` modal when a rich analysis is already on screen** — the modal hides the tables the user is deciding against; reserve it for standalone choices. **Scope the subagent model to the task** — high-reasoning work → Opus, ordinary/complicated work → Sonnet, trivial mechanical work → Haiku; don't spend Opus on a rename or ship a smaller model on judgment-heavy synthesis. **Agent-first testing** — the agent autonomously runs every verification it can (perf/SLO probes, log/API checks, accessibility passes); the human is tester of last resort, only for device-only interactions, subjective UX, or credentials only they hold. Add entries here as harness behaviors get learned.
7. **Status** — current state of the project. Updated as tooling, architecture, and the first specs land.

## Path-scoped `CLAUDE.md` files

When to create one: when a directory accumulates invariants distinct from the root. Examples: `docs/CLAUDE.md` for documentation conventions (ADR shape, research frontmatter, no ephemeral artifacts), `apps/<app>/CLAUDE.md` for app-specific implementation conventions.

Loaded automatically when files in that path are touched. Keep terse — same budget pressure as the root.

Shape, in order:

1. **Identity** — what this directory contains and is for.
2. **Invariants** — must-follow rules specific to this path.
3. **Patterns** — common idioms, file locations.
4. **Out of scope** — what does not belong here.

## Canonical-sources registry

File: `docs/canonical-sources.md`.

**Purpose.** One source of truth per recurring fact. Every other document writes a pointer, not a copy. Drift becomes a pointer-update problem instead of a find-all-restatements problem.

**Format.** A markdown table with columns: `Fact class | Canonical source | Pointer form to use elsewhere | Notes`.

**Pointer convention.** Two tiers, both starting with the literal prefix `Canonical source:`. Section anchor optional — include when the canonical owner has named sections; omit for single-topic files.

- **Tier 1 (reference).** Used when the non-canonical doc names the fact by label without quoting or restating it.

  ```
  Canonical source: <path> § <section>.
  ```

- **Tier 2 (restatement guard).** Used when the pointer replaces what would otherwise be a copy — an enumerated list, schema, matrix, or policy statement. The trailing `Do not restate here.` reminds future authors not to reintroduce the content.

  ```
  Canonical source: <path> § <section>. Do not restate here.
  ```

Use Tier 2 whenever the pointer stands in for content that would otherwise be duplicated; Tier 1 otherwise. The registry itself is the only document exempt — it is the root.

**Plain text in repo, hyperlinked in Linear.** In-repo markdown uses plain-text pointers (paths, not URLs). Linear-rendered surfaces may use hyperlinks because human stakeholders read them there.

**Interim entries.** A row may point at a section inside a research report or other placeholder while the dedicated canonical home is still being created. The `Notes` column flags interim status with the planned move target. Closing out an interim entry is a normal change — update the row, update the placeholder to a pointer back at the new home.

**New recurring fact** → add a row in the same PR that introduces it. Adding a row is a normal change, not a ceremony.

**Enforcement.** Manual at MVP. A drift-checker script goes on the trigger list once the first cross-doc drift incident is caught.

## ADRs

Location: `docs/decisions/YYYY-MM-DD-<slug>.md`.

**Shape (fixed).** Uniform shape keeps history scannable.

```
# <Title>

## Context
## Decision
## Alternatives
## Rationale
## Impact
```

- **Context** — what problem this decision addresses; what changed that triggered the decision.
- **Decision** — the picked approach, in enough detail to act on without re-reading the alternatives.
- **Alternatives** — what was considered and rejected, with one-line reasons. Future readers ask "did you consider X?" — this section is the answer.
- **Rationale** — why the picked approach beats the alternatives. Names the principles being applied.
- **Impact** — what else must change: canonical-sources rows, `CLAUDE.md` edits, downstream docs, follow-up ADRs.

**Trigger.** Every architectural, product, or workflow decision. Filed immediately, not retrospectively. Check existing ADRs before proposing anything that might contradict one.

**Cadence.** When a decision is made in conversation, the ADR lands in the same session as the decision. The Impact section's enumeration of downstream edits is the working checklist for closing the loop.

## Context budget and tiered documentation

**Budget.** Declared-slice file-content reads for downstream implementation work target **≤7,000 tokens**, measured via `tiktoken` cl100k_base.

**Pattern: tiered documentation.**

- **Always-loaded tier** — root `CLAUDE.md` and path-scoped `CLAUDE.md` files. Kept terse.
- **On-demand tier** — ADRs, architecture docs, specs. Loaded when relevant. Kept terse; depth links to lower tiers.
- **Deep-reference tier** — research reports, extended design docs. Loaded only when the on-demand tier points to them.

**Scope.** The budget counts file-content reads only: design docs, validation slices, code patterns, code-quality references, path-scoped `CLAUDE.md` auto-loads.

**Exclusions.** Tool-call XML, grep output, system reminders, MCP tool schemas, the handoff prompt. They vary unpredictably per task and harness; including them would make the budget unmeasurable.

**Enforcement.** Manual at MVP. Drift-checker on the trigger list.

The pointer convention in `docs/canonical-sources.md` (Tier 1 reference vs Tier 2 restatement guard) is the bridge between tiers.

## Roadmap and workflow hierarchy

**Hierarchy.**

- **Phase** — grouping of features sharing a goal/milestone. Surface: row in `docs/roadmap.md` + Linear Initiative (manual UI prereq — see § Linear coupling) + one long-lived branch `phase-<n>-<kebab-phase-slug>`.
- **Feature** — smallest coherent slice of user-observable behavior. Surface: one spec directory + one Linear Project. No feature-level branch — features share the phase branch.
- **Task group** — numbered section in `plan.md`. Surface: one Linear Issue (e.g. `ENG-N`) + one commit on the phase branch.
- **Tasks within a group** — checklist on the parent issue. Promote to sub-issue only if a specific task becomes a tracked blocker on its own.

**Branching.** One long-lived branch per *phase*, named `phase-<n>-<kebab-phase-slug>`. Engineering commits for the phase land on that branch — one commit per task-group Issue (`ENG-N`). A single PR opens at phase completion (all the phase's Issues marked Done in Linear) into `main`. Phase-independent work — ADRs, kickoff prompts, `CLAUDE.md` edits, repository governance — lands on `main` directly, never on a phase branch. An earlier iteration of this pattern used one branch per feature; the phase branch reduces PR ceremony and keeps a phase's commits contiguous.

**Roadmap shape (`docs/roadmap.md`).** Sequential phases. Per-phase block: `H2 title` + **Goal** + **Rationale** + **Exit criteria**. Preamble names the workflow ADR as canonical for shape, states the mutability rule, cross-references the polish backlog.

**Mutability.** Undelivered phases are mutable — reorderable, rescopable, removable, addable. Delivered phases are history and are not rewritten. The roadmap reflects current intent, not commitment to every future row.

**Infra phasing.** Just-in-time, first-use not first-need. Contiguous infra phases can be combined to reduce ceremony.

**UI phasing.** UI lives in feature specs (no dedicated UI phase) except a minimal design-system-foundation phase up front to avoid retrofit on the first user-facing feature.

## Spec-driven pipeline

No feature implementation without a spec in `specs/`. Specs land paired with evals. Just-in-time — written when entering a phase, not upfront. The spec directory is scaffolded by the `roadmap-phase-kickoff` skill (see § Skills), which resolves the roadmap heading, opens the phase branch, elicits content from the user, and writes the four artifacts.

**Spec directory.** Path: `specs/YYYY-MM-DD-<feature-slug>/`. Date is the spec's authoring date, not the engineering-completion date. Required contents:

- `requirements.md` — scope, decision context, the user-observable outcome that defines "done."
- `plan.md` — numbered task groups. **Each top-level group begins with a `**Linear:** *(pending publish)*` line directly below the heading**; the publish-spec skill replaces the placeholder with the assigned `ENG-N (Title)`. Additive-only — once replaced, the line is never rewritten.
- `validation.md` — intent-level acceptance criteria. What the quality agent checks to confirm the feature behaves as the requirements specified. Often manual or scenario-based. **NFR enumeration section required** — pointer at the canonical NFR doc + per-row verification path (or reasoned skip).
- `evals/` — programmatic specifications the engineering agent must satisfy. Eval-author agent owns. Eval IDs follow `EVAL-<FEATURE-SLUG-PREFIX>-<seq>` (e.g., `EVAL-PROV-001`) — the prefix is short, stable, and per-spec; IDs are stable identifiers so `validation.md` and Linear citations stay valid as the eval file evolves.

**Unit tests are not evals.** Unit tests verify code-level correctness and live with the code; evals verify feature-level specification compliance and live with the spec. Engineering agent owns unit tests.

**Path-scoped `specs/CLAUDE.md`.** Lands when the first spec is authored. Encodes the directory-shape, NFR-gate, evals-vs-unit-tests, Linear-coupling, and additive-only invariants so the engineering agent loads them automatically when touching files under `specs/`.

## Agent roles

The artifact split (`requirements.md` / `plan.md` / `validation.md` / `evals/`) maps to an agent split. Each agent owns one artifact; conflating any two collapses the separation of concerns.

- **Lead agent (PM).** The one in conversation with the user. Holds scope discipline, raises technical quality concerns, drafts ADRs, edits the roadmap, captures polish items, updates memory inline as state changes. Does not implement features — orchestrates the downstream agents through artifacts and Linear. Authors `requirements.md` with the user.

- **Eval-author agent.** Owns `specs/<feature>/evals/`. Reads `requirements.md` and produces programmatic specifications the engineering agent must satisfy. Evals are machine-runnable and feature-level, not code-level.

- **Engineering agent.** Owns `specs/<feature>/plan.md` execution and the code itself, including unit tests. Reads `requirements.md` + `evals/` as primary working context. Implements task group by task group; updates the Linear Issue (`ENG-N`) per task group as it completes.

- **Quality agent.** Owns `specs/<feature>/validation.md`. Runs intent-level acceptance checks — often manual or scenario-based — to confirm the feature behaves as the requirements specified. Signals branch-ready-to-merge when validation passes.

**Coordination.** Agents coordinate through the spec directory (source of truth for *what*) and Linear (source of truth for *status*), not through direct messaging. Linear Issues update as task groups close; the spec directory is read-mostly during engineering — substantive changes mean a new spec, not an in-place edit (see additive-only `/publish-spec` rule below).

## Polish backlog

File: `docs/polish-backlog.md`. Canonical capture point for out-of-scope polish, refinement, and improvement ideas surfaced during feature work.

Items are **candidates, not commitments**. Three exit paths:

1. Folded into an in-flight feature's `plan.md` as an additional task group, when the feature touches the relevant area. The `/publish-spec` additive-only rule makes this clean.
2. Specified as their own feature phase, when large enough.
3. Batched into a pre-launch quality-sweep phase.

Root `CLAUDE.md` § Tight scope discipline carries a **Capture, don't expand** instruction directing the agent to write here rather than expand a spec. Backlog is the pressure valve that keeps scope tight without losing valid ideas.

**Not Linear.** Pre-committed ideas are not statuses; clutters the status view; conflicts with "Linear is the source of truth for status."

---

## Operations directory

Directory: `docs/operations/`. Recording artifacts created and updated during feature execution: provisioning ledgers, rollback runbooks, restore drills, per-incident files. The recording home for verification outcomes that aren't code-resident — vendor dashboard observations, plan tiers, regions, drill timings, gap escalations against NFR commitments.

**Recording, not deciding.** ADRs decide; specs scope; operations records what actually happened. No new architectural decisions land here — drift to ADRs if a decision is needed. The path-scoped `docs/operations/CLAUDE.md` enforces this on every load.

**Provisioning-ledger pattern.** Each phase that provisions infrastructure owns one ledger file: plan tier, region, credentials reference (not secrets themselves), env-var inventory, per-row gap against NFR commitments. Gap escalations are first-class — silent absorption defeats the purpose of the ledger.

**Secrets never live here.** Credentials *references* (env-var names, application IDs, bucket identifiers) are recorded; the values themselves stay in vendor dashboards.

**Pointer-not-copy.** Facts canonical elsewhere (NFR targets, ADR decisions, schema definitions) are pointed at — operations files reference, they don't restate.

Files: `provisioning-ledger.md` (phase-scoped), `rollback.md`, `restore-drill.md` (runbook-style with recorded drill timings). Per-incident files use `YYYY-MM-DD-<incident-slug>.md` if/when they accumulate.

## Linear coupling

- **Phase** → Linear **Initiative**, created **manually in the Linear UI** before the first feature in that phase publishes (~30 seconds per phase). Initiative name matches the `docs/roadmap.md` heading verbatim (e.g., `Phase 2 — Backend infrastructure`).
- **Feature** → Linear **Project**, named to match the spec directory's descriptive form (title-cased slug). Created by `/publish-spec` and linked to the phase Initiative via `addInitiatives: ["<phase-name>"]`.
- **Task group** → Linear **Issue** (`ENG-N`). Description points at `specs/YYYY-MM-DD-<feature-slug>/plan.md` group N. No restating of requirements in Linear.

**Why manual Initiative creation.** Linear has two milestone-like concepts: *Project Milestones* (sub-stages within a single Project) and *Initiatives* (workspace-level groupings of Projects). Phase semantics — workspace-level, multi-project, parallel to roadmap rows — match Initiative, not Project Milestone. The Linear MCP exposes Project Milestone CRUD but no `save_initiative` / `list_initiatives` tools; Initiatives are referenceable only via `save_project.addInitiatives` (accepts names) and the `initiative` filter on `list_projects`. Manual UI creation is the only path until MCP closes the gap. Project Milestones remain available for intra-feature staging if needed.

**Spec directory = source of truth for *what*. Linear = source of truth for *status*.**

**Publish step.** A slash command (`/publish-spec`) is the only mechanism that creates Linear items from the spec directory. Trigger: after `requirements.md`, `plan.md`, `validation.md`, and `evals/` are finalized and the NFR gate is passed. The skill reads the spec directory, creates the Project (linked to the pre-existing Initiative) and an Issue per task group via the Linear MCP, and writes the assigned `ENG-N (Title)` annotations back into `plan.md` over the `*(pending publish)*` placeholders.

**Idempotency: additive-only.**

- New task groups in `plan.md` (with `*(pending publish)*` placeholder) → new Linear Issues.
- Existing task groups already annotated with `ENG-N` → never modified, never deleted by re-running `/publish-spec`.
- If a task group needs to be removed or substantively reshaped, do it via a new spec (or a follow-up feature), not by editing an already-published group.
- If the phase Initiative is missing in the Linear UI when `/publish-spec` runs, the skill aborts cleanly with a clear message — fail-fast on the manual prereq.

**Reference convention.** Pair `<ID> (<Title>)` on first mention in any human-readable surface — chat replies, commit messages, PR descriptions, ADRs, ledger entries, Linear comments. Applies to every Linear item across every team prefix. Bare ID after first mention is fine.

## Skills

Slash-command skills carry recurring workflow load. Both tiers live in the project's `.claude/skills/`; they differ in how they're maintained:

- **Cross-project utility skills — vendored from a shared upstream.** `handoff-kickoff` (end-of-session trunk continuity), `resume` (next-session context load), `worktree-handoff` (branch-scoped, local-ephemeral handoff), `step-table` (tables-over-prose formatting authority). Maintained in a shared repo (`github.com/benhudelson/skills`) and vendored into each project at `.claude/skills/` via `git subtree` (see *Vendoring* below), so they ship with the repo — a plain clone has them, no global install required. They read project-local config (root `CLAUDE.md` directives, the memory dir, git state) but encode no project-specific content. (They also load from a global `~/.claude/skills/` when one exists, but vendoring keeps the project self-contained.)
- **Project-specific workflow skills — authored per project.** e.g. `roadmap-phase-kickoff` (roadmap row → phase branch + scaffolded spec directory) and `publish-spec` (finalized spec → Linear). Written directly in `.claude/skills/` alongside the vendored utility skills. These name project artifacts (`docs/roadmap.md`, the spec-directory shape, the Linear team) directly, so each project authors its own from the § Skills contracts rather than inheriting another project's — the shared upstream carries only the utility skills, not these.

**Placement test.** Would this skill behave identically on an unrelated project? It belongs in the shared upstream (vendored in). Does it reference this project's roadmap, spec pipeline, or tracker? Author it here as a project skill.

**Vendoring the utility skills (git subtree).** Vendored — not submoduled — so they're real files in the tree that survive a plain clone and leave room for project-authored skills in the same directory (a submodule would monopolize `.claude/skills/` and arrive empty until `git submodule update --init`). Install:

```
git subtree add --prefix=.claude/skills https://github.com/benhudelson/skills.git main --squash
```

The shared upstream carries only the four utility skills (an allowlist `.gitignore` keeps it pared down), so the add needs no cleanup — you get `handoff-kickoff`, `resume`, `worktree-handoff`, `step-table`. Update later with:

```
git subtree pull --prefix=.claude/skills https://github.com/benhudelson/skills.git main --squash
```

A pull brings only those four skills — no cleanup needed.

This section captures the rebuild contract for each skill so the SKILL.md files can be regenerated on a new project from this document alone.

### Common skill conventions

- **File path.** All skills live at `<project-root>/.claude/skills/<skill-name>/SKILL.md` — utility skills vendored there via subtree, workflow skills authored there directly (see *Vendoring* above). They also load from a global `~/.claude/skills/<skill-name>/SKILL.md` when present. The directory name is the skill's invocation name (`/handoff-kickoff`, `/publish-spec`).
- **Frontmatter.** YAML with `name` and `description`. The description must list the trigger phrases the harness matches against (e.g., "wrap this session", "write a kickoff prompt", "publish the spec"). Verbose descriptions improve trigger reliability.
- **Project-local override pattern.** Skills are global; project-specific behavior comes from grepping the project's root `CLAUDE.md` for directives (e.g., `handoff-path:`) or reading project files (`docs/canonical-sources.md`, `docs/roadmap.md`). Never hard-code project-specific values into the SKILL.md.
- **No attribution.** Skills must scrub `Co-Authored-By` and "Generated by Claude" footers from any commits they create — same rule as everywhere else.

### Skill: `handoff-kickoff` (global utility)

**Purpose.** Generate a next-session kickoff prompt that hands off in-flight *trunk* work to a fresh agent without context rot. Branch-scoped work belongs in `worktree-handoff` (below) — if invoked on a non-default branch, note that a worktree handoff may fit better and confirm before generating a trunk kickoff.

**Trigger phrases.** "wrap this session", "write/update the kickoff prompt", "hand this off to the next agent", "context is rotting", "prep a fresh agent".

**Output path resolution (in order; stop at first match).**
1. Explicit override at `.claude/handoff-config` (single line: `path: <relative-path>`).
2. Grep root `CLAUDE.md` for `handoff-path:` directive.
3. Existing convention — reuse a directory if it already contains `*kickoff*.md` files (`docs/kickoff-prompts/`, `docs/handoffs/`, `.claude/handoffs/`, or legacy `docs/transcript-reports/`).
4. Default `docs/kickoff-prompts/`. Create the directory if missing.

**Filename.** Single canonical file, overwritten each session-boundary regen — resolve via the `handoff-file:` directive in root `CLAUDE.md`, default `next-session-kickoff.md`. No dated filenames, no `-vN` versioning; git history is the audit trail for prior snapshots. Overwrite the existing file (its prior content becomes the new commit's parent); never `--amend` an existing kickoff commit. Kickoffs commit **and push** to `main` (see step 10); from a phase branch, read the latest via `git show main:<path>` rather than checking out `main`.

**Behavior contract (steps).**

1. **Continuous-learning sweep (runs first, before the handoff brief).** Review the transcript since the prior kickoff's anchor and extract the session's lessons into three categories — *corrections* (the user fixed a wrong output/assumption), *operational procedures* (a "from now on…" process rule), *preferences* (format/tone/tooling likes). De-dup against existing memory, `MEMORY.md`, root `CLAUDE.md`, and `settings.json` hooks first — surface only genuinely new items. Present each surviving item **one at a time** via `AskUserQuestion` (never batched), offering concrete durable mechanisms as options: write/update a memory file (`feedback`/`user`, with `**Why:**`/`**How to apply:**` for feedback), add a `CLAUDE.md` directive, configure a hook via the `update-config` skill (required for any automated "whenever X" behavior — memory can't enforce those), or edit the relevant skill. Apply each choice immediately. Writes to `settings.json` and root `CLAUDE.md` are **atomic** (temp file + `mv`) and `MEMORY.md` is **regenerated** from the memory dir's frontmatter, never hand-appended — other worktrees may run this sweep concurrently against the same global files. This is the continuous-learning loop; skipping it lets session lessons evaporate.
2. **Lead-agent brief.** The lead writes a tight in-conversation brief covering: in-flight decisions (mid-discussion items), verification debt (subagent claims not independently checked), failed approaches, open questions raised but not filed, parked items waiting on a human, and **uncommitted/untracked working-tree state** (`git status --porcelain` — the anchor SHA does not capture it).
3. **Optional ledger sweep.** If the project uses an epic-ledger system (look for `docs/epic-ledgers/README.md`), sweep before delegating: write any unflushed `IN`-tagged recommendations from the session as ledger entries. Skip if the project doesn't use this system.
4. **Synthesis subagent.** Delegate the kickoff write to a `general-purpose` agent **on the Opus tier** (`model: opus` — verify-before-strip and the Applied/Abandoned/Waiting classification are judgment-heavy, and handoffs often close a session running a smaller coding model). Subagent reads: prior kickoff in the resolved dir, root `CLAUDE.md` (for current invariants), the lead brief. Subagent verifies prior-kickoff "open work" / "what landed" claims against `git log <prior-anchor>..HEAD`, file existence, Linear MCP queries, eval file contents — items that fail verification carry forward tagged `[unverified]`.
5. **Classify each prior item** as *applied* (strip from open work; capture in "what landed"), *abandoned/changed* (one-line note in "Closed / superseded"), or *waiting on human* (carry forward verbatim).
6. **Pull session deltas** since the prior anchor: new ADRs (filename + one-line gist), new/modified specs and evals, Linear status changes, new commits with subject lines.
7. **Assemble the kickoff** in the section order below.
8. **Length guard.** Soft cap ~200 lines. If exceeded, split into a sibling `YYYY-MM-DD-handoff-digest.md` and link from the kickoff. Warn the user.
9. **Prune stale worktree handoffs (default branch only).** When generating on the default branch (trunk authority), list `<git-common-dir>/claude/worktree-handoffs/*.md`; for each, derive its branch and **delete** the file if the branch no longer exists (merged-then-deleted or abandoned). Report — don't delete — any whose branch still exists but is >30 days stale. Skip if the dir is absent.
10. **Write, commit, push, report.** Commit only if inside a git work tree and the path isn't gitignored. Stage the new kickoff *plus any other untracked `*kickoff*.md` files in the same dir* — never bundle in unrelated changes. **Then push to `main`: `git push origin HEAD:main`** (lands on remote `main` regardless of the checked-out branch; a normal fast-forward — never force). If the push is rejected as non-fast-forward, report `pushed: failed (main diverged)` and leave the local commit for the user to reconcile. Skip the commit (with reason) if any precondition fails; never use `--no-verify`.

**Kickoff prompt structure** (sections, in order — see also § Handoff and kickoff for the full structural rationale):
1. Anchor (HEAD SHA, date, branch, working dir, prior kickoff path, commit range).
2. Hard operating rules (pulled fresh from root `CLAUDE.md`, **not** copy-forwarded from the prior kickoff — avoids stale-rule drift).
3. What landed this session (verified deltas only; grouped by ADR / spec / eval / Linear / commit).
4. In-flight at handoff (from the lead brief — the resume-mid-decision section).
5. Verification debt — **a one-line pointer to `memory/project_verification_debt.md`**, not an inline table (see § Handoff narrative routing in root `CLAUDE.md`).
6. Failed approaches / pitfalls (carries forward across sessions until the underlying issue is fixed).
7. Open work — carry-forward, classified (each entry tagged with which prior kickoff first raised it). Parked / waiting-on-human items are **pointed at `memory/project_pending_decisions.md`**, not inlined.
8. Closed / superseded this session.
9. Out of scope for next session (explicit non-goals).
10. Context load order (newest canonical first).
11. **Standing instructions for the next agent** — required verbatim block on inline memory updates (see below).
12. **START HERE** — recommended next topics with rationale; ends with "Wait for the user's answer. Do not start work until they pick a topic."

**Required standing instruction (every kickoff).** Verbatim block, top-level section labelled `## Standing instructions for the next agent`, placed immediately before `## START HERE`:

> **Always update or remove memory the same turn an item changes state.** When any tracked item changes state (a commit lands, an epic transitions stage, a decision is made, a blocker is resolved, an ADR is filed, an item is dropped or deferred), update the relevant memory file inline in the same turn. **When an item fully closes, *delete* the entry — do not leave "done" or "resolved" markers; closed entries accumulate and obscure what's actually open.** Cite the commit SHA / Linear ID / ADR slug for the state change in your conversation reply, not in the memory entry. If the change invalidates this kickoff prompt's "what landed" or "open work" sections, flag it to the user rather than silently editing the kickoff — kickoffs are historical artifacts; memory is the live view.

This block is non-negotiable. Stale memory leaks into next-session kickoffs and produces wrong premises.

**Anti-patterns.**
- Don't trust the agent's TodoList — completion claims must be verified against repo / Linear state.
- Don't copy hard operating rules from the prior kickoff — pull fresh from `CLAUDE.md`.
- Don't preserve historical kickoffs in-tree — overwrite the single canonical file; git history is the audit trail. Never reintroduce dated or `-vN` filenames.
- Don't inline verification debt or parked items — route them to their memory files and emit pointers (§ Handoff narrative routing).
- Don't drop parked items because they were also parked last session — that's exactly what context rot loses.
- Don't drop verification debt — carry forward tagged `[unverified]` if it can't be confirmed.
- Don't write a verbose narrative — the next agent needs a checklist with file paths and IDs.
- Don't skip the continuous-learning sweep — it runs every launch, before the brief; skipping it evaporates the session's lessons.
- Don't batch the sweep items — one `AskUserQuestion` per item, even for yes/no; the user decides each mechanism.
- Don't claim a correction is "stored" without a durable mechanism — a memory/hook/directive/skill edit must actually be written; an automated "whenever X" needs a hook, not memory.

### Skill: `worktree-handoff` (global utility)

**Purpose.** Branch-scoped, local-ephemeral sibling of `handoff-kickoff`. Captures **one feature branch in flight** as local scratch so a fresh agent on the same branch resumes cleanly. It **never commits and never pushes** — that is the defining difference from `handoff-kickoff`, and it is what lets many worktrees wrap concurrently without contending for a ref.

**Trigger phrases.** "wrap this worktree", "hand off this branch/feature", "park this worktree", "prep a fresh agent for this feature", "context is rotting on this branch". If invoked on the **default branch**, stop and defer to `handoff-kickoff`.

**Deltas from `handoff-kickoff`.** This skill specifies only its differences; the shared mechanics — continuous-learning sweep, verify-before-strip, section schema, length guard, standing-instruction block — are followed verbatim from `handoff-kickoff` so the two never drift.

1. **Confirm branch + resolve the local path.** Current branch via `git branch --show-current` (empty/detached → abort). Default branch via `git symbolic-ref --short refs/remotes/origin/HEAD` (fallback `main`); if current == default → defer to `handoff-kickoff`. Write to `<git-common-dir>/claude/worktree-handoffs/<branch-slug>.md` (`git rev-parse --git-common-dir`; branch `/` and unsafe chars → `-`). **Why the common dir:** reachable from every linked worktree, survives `git worktree remove`, and is never tracked (it lives inside `.git/`, so no commit and no gitignore needed).
2. **Run the continuous-learning sweep** verbatim from `handoff-kickoff` step 1 — it's global and orthogonal to which handoff is being written.
3. **Collect the brief + verify-before-strip**, scoped strictly to this branch: in-flight decisions on this feature, this branch's verification debt, failed approaches on this branch, feature-specific open questions, parked items. Anchor deltas to the branch (commits since the prior handoff's anchor; merge-base with the default branch).
4. **Assemble** with the shared section schema, plus: the **Anchor** names the branch, its latest SHA, and its merge-base with the default branch; a **Relationship to trunk** line states what must graft into the trunk handoff when the branch merges; include the standing-instruction memory block.
5. **Write and report — NO commit, NO push.** Write to the resolved local path; never `git add`/commit/push. Report path, line count, branch + anchor SHA, any `[unverified]`, digest-split y/n, items flagged for trunk promotion, and an explicit note that it was **not** committed.

**Promotion to trunk.** Learnings already reach global memory via the sweep. Open work that outlives the branch is flagged as promotion candidates; the graft into the trunk handoff happens next time `handoff-kickoff` runs on the trunk (which also prunes this file once the branch is gone).

**Anti-patterns.**
- Don't commit or push it — local-ephemeral by design.
- Don't write it inside the working tree — use the git common dir so it's shared across worktrees and survives `git worktree remove`.
- Don't run it on the default branch — that's `handoff-kickoff`'s job; defer.
- Don't duplicate trunk-wide state — scope strictly to this branch.
- Don't re-derive the shared mechanics — reference `handoff-kickoff`'s named sections so the two stay in lockstep.

### Skill: `publish-spec` (project-local workflow)

**Purpose.** Publish a finalized feature spec to Linear: reference the phase Initiative (manual prereq), create the feature Project, create one ENG-N Issue per `plan.md` task group, write the assigned IDs back into `plan.md`. Additive-only.

**Trigger phrases.** "publish the spec", "push <feature> to Linear", "create ENG issues for <spec>", "run /publish-spec".

**Preconditions.** A finalized `requirements.md`, `plan.md`, `validation.md`, and `evals/` exist in the spec directory. The NFR gate passed (every applicable NFR row in `validation.md` has a verification path). Specs that aren't review-clean must not be published — once an Issue lands in Linear, the published task group is immutable per the additive-only rule.

**Idempotency contract.**
- Re-running on a spec where some groups already have ENG-N annotations: those groups are skipped (no Linear writes, no `plan.md` edits). Only groups with the literal `**Linear:** *(pending publish)*` placeholder are processed.
- Re-running where the Project doesn't exist yet: create it.
- Re-running where the Project exists: reuse it; never create a duplicate.
- The phase Initiative is a manual prereq created in Linear UI before first invocation in a phase. Skill aborts cleanly if missing.
- Never modifies or deletes an existing ENG-N annotation or its corresponding Linear Issue. Removal/reshape after publish goes via a new spec.

**Behavior contract (steps).**

0. **Locate the spec directory.** Use the user-named path or ask. Must be `specs/YYYY-MM-DD-<slug>/` with all four required artifacts. Abort with a clear message if any artifact is missing.
1. **Identify the phase.** Read `requirements.md` for an explicit phase reference. Propose to the user and confirm. If ambiguous, ask. Read `docs/roadmap.md` to recover the phase's full name (e.g., "Phase 2 — Backend infrastructure"). That string is the Initiative name.
2. **Linear preflight (read-only).** Use the Linear MCP (`mcp__claude_ai_Linear__*` in the current environment; adjust if the MCP server is registered under a different name). Inspect:
   - **Team** via `list_teams`. If exactly one matches the convention (e.g., `ENG`), use it; else ask. Capture team ID.
   - **Initiative** — no `list_initiatives` MCP tool exists. Probe indirectly via `list_projects` filtered by `initiative: "<phase-name>"`. Non-empty confirms; empty is ambiguous (Initiative may exist with zero projects, or not at all). Surface to the user in Step 3.
   - **Project** via `list_projects` filtered by team. Match by name. Found → reuse with ID; else → create.
   - **Existing issues under the Project** (if it exists) via `list_issues` filtered by Project. Cross-reference each Issue title against `plan.md` task-group headings; matches mark groups as already-published.
3. **Propose the publish plan to the user before any Linear writes.** Show: spec path, team, Initiative (with Step 2 probe result and the manual-prereq reminder), proposed Project name (descriptive title-cased form of the spec slug, user-overridable), Project description (one-line `Spec: specs/<spec-dir>/`), Issues to create (one row per `*(pending publish)*` group with proposed title and `**Done when:**` line), Issues to skip (already-annotated or matched). **Wait for explicit user confirmation, including confirmation that the Initiative exists in the Linear UI.** Do not proceed on tepid signals.
4. **Create the Project (if needed).** `save_project` with the confirmed name, description `Spec: specs/<spec-dir>/`, `addInitiatives: ["<phase-name>"]`, team ID. If `addInitiatives` fails (Initiative not found), abort with a clear message instructing the user to create the Initiative in Linear UI and re-invoke. Capture project ID.
5. **Create the Issues.** For each `*(pending publish)*` task group (and not already matched in 2), `save_issue` with:
   - **Title:** group heading minus `## N. `.
   - **Description (markdown, pointer-style — no requirements restatement):**
     ```
     Spec: specs/<spec-dir>/
     Plan: specs/<spec-dir>/plan.md § N. <Heading>

     <one-line group intro paragraph copied verbatim from plan.md>

     ## Checklist
     - [ ] <bullet 1>
     - [ ] <bullet 2>
     ...

     ## Done when
     <plan.md "Done when" line>

     ## Depends on
     <plan.md "Depends on" line>
     ```
   - Project ID from Step 4, team ID from Step 2.

   Capture each `(ENG-N, Title)` pair.
6. **Write ENG-N annotations back to `plan.md`.** Replace each group's `**Linear:** *(pending publish)*` line with `**Linear:** ENG-N (Title)` (paired form, first-mention rule). **Additive-only guard:** only the literal placeholder is replaced; lines already containing an ENG-N annotation are not touched. Do not commit — the user owns the commit.
7. **Report.** Spec path published; Initiative (referenced | missing-aborted); Project (ID + name + created/reused); Issues created (count + bulleted ENG-N list); Issues skipped (count + reason); `plan.md` lines modified (count); any failures.

**Anti-patterns.**
- Don't write to Linear before user confirmation in Step 3 — Linear writes aren't local and aren't free to undo.
- Don't overwrite an existing ENG-N annotation — additive-only is non-negotiable; it's how the workflow keeps repo and Linear in sync without two-way sync.
- Don't restate `requirements.md` in any Linear surface — Project and Issue descriptions are pointers.
- Don't create a second Project with the same name under the same team — always reuse.
- Don't bundle the `plan.md` write-back with other edits — the skill writes the file and stops.
- Don't publish a spec missing `validation.md` or `evals/` — the NFR gate and evals pipeline assume publish only happens on review-clean specs.
- Don't infer the phase silently — propose-and-confirm before the first Linear write, even when `requirements.md` names the phase clearly.
- Don't attempt to create the Initiative via MCP — no `save_initiative` tool exists; it is a manual prereq.

### Skill: `roadmap-phase-kickoff` (project-local workflow)

**Purpose.** Turn a roadmap row into a spec ready for the pipeline: resolve the referenced heading in `docs/roadmap.md`, open the phase branch `phase-<n>-<kebab-phase-slug>`, elicit the spec content from the user via the AskUserQuestion tool (no inference), and scaffold `specs/YYYY-MM-DD-<feature-slug>/` with `requirements.md`, `plan.md`, `validation.md`, and `evals/` per `specs/CLAUDE.md`. This is the upstream bridge to `/publish-spec`.

**Trigger phrases.** "start the next phase", "kick off phase N", "begin Phase N", "open the next phase branch", "scaffold the spec for Phase N", or a roadmap-heading reference paired with explicit intent to begin. Do **not** fire on ambient mentions of phase numbers without an action verb.

**Invariants.**
- **No file writes before the user's answers are in hand.** Branch creation is the only mutation allowed before elicitation completes.
- **No auto-commit, no auto-push.** The user owns the first commit on the new branch.
- **No inference of spec content.** Every section is sourced from the user's answers. A section with no answer gets the heading plus an `*(awaiting user)*` placeholder, surfaced in the final report — never invented prose. In particular, do not pre-pick NFR rows by reading the canonical NFR doc; the row choice is the user's.
- **Fail loudly.** Unresolvable phase reference, an already-existing branch (local or `origin/`), or an already-existing spec directory → abort with a clear message naming the conflict. Never auto-suffix (`-v2`, `-redo`).
- **Four-artifact structure is hard.** Never collapse to a single mega-file or a condensed three-file variant — `/publish-spec` depends on the shape.

**Behavior contract (steps).**
0. **Preflight.** Confirm repo cwd; confirm the working tree is clean or safe to carry onto a new branch; resolve today's date via `date +%Y-%m-%d` (do not derive from context strings) for the spec dir name.
1. **Resolve the phase** against `docs/roadmap.md` — grep `^#+ Phase ` headings, match by number or title fragment; "the next phase" = lowest-numbered phase whose exit criteria aren't delivered. Ambiguous → ask. Capture the heading verbatim.
2. **Derive names and pre-check existence.** `branch_name = phase-<N>-<title_slug>`; `feature_slug = <title_slug>` (no `phase-N-` prefix); `spec_dir = specs/<today>-<feature_slug>/`. Abort if branch (local or origin) or spec dir already exists.
3. **Create the branch** (`git checkout -b <branch_name>`). No push, no upstream tracking.
4. **Elicit via AskUserQuestion** — collect answers for every section of all four artifacts (≤4 question calls plus at most one free-form prose prompt). Wait for the user to answer before any write.
5. **Write the spec directory** mirroring the established artifact shapes (Identity / Decision context / In scope / Out of scope / done-definition for `requirements.md`; numbered task groups each with a `**Linear:** *(pending publish)*` line for `plan.md`; behavioral-acceptance table + NFR enumeration + sign-off conditions for `validation.md`; `evals/README.md` + one file per eval). Do not commit.
6. **Report** as a tight table: phase resolved, branch created, spec directory, files written, sections left `*(awaiting user)*`, next move (`git add && commit`, then `/publish-spec` once review-clean). End with a one-line confirmation that nothing was committed or pushed.

**Anti-patterns.**
- Don't invent spec content — inferred prose is the failure mode this skill exists to prevent.
- Don't auto-commit, auto-push, or auto-suffix on collision.
- Don't skip the AskUserQuestion step even when the user hinted at content earlier — eliciting via the question system is the contract.
- Don't commit the spec to `main` — it belongs on the phase branch; only phase-independent housekeeping lands on `main`.

### Skill: `resume` (global utility)

**Purpose.** Restore session context by loading the handoff that matches the current branch — the trunk kickoff on the default branch, the branch's local worktree handoff on a feature branch — plus the memory files it points at, summarize current state, and wait for direction. Read-only; orients, does not act.

**Trigger.** Only on explicit `/resume`. Treat ambient phrasing ("let's continue", "pick up where we left off", "what's the state") as conversation, not a trigger — the slash command is the user's deliberate opt-in.

**Behavior contract (steps).**
0. **Resolve which handoff applies (branch-aware).** Not in a git repo → read the trunk fallback and stop (no worktree handoffs without git). Else capture current branch (`git branch --show-current`) and default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, fallback `main`). Compose the **trunk kickoff path** (grep `handoff-path:`/`handoff-file:`; fallback `docs/kickoff-prompts/next-session-kickoff.md`) and the **worktree handoff path** (`<git-common-dir>/claude/worktree-handoffs/<branch-slug>.md`). On the default branch the trunk kickoff is primary; on a feature branch the worktree handoff is primary **if it exists**, else fall back to the trunk kickoff and say so.
1. **Read the primary handoff end-to-end.** Trunk kickoff: on the default branch read the working tree; from any other branch read via `git show <default>:<path>` (never check out the default branch, never copy into the branch tree). Worktree handoff: read straight from the local common-dir path (never tracked in git, so no `git show` form).
2. **Index other handoffs + flag stale (read-only).** Print a one-line awareness index of the other worktree handoffs plus the trunk kickoff, so concurrent sibling sessions are visible without loading them. For each worktree handoff whose branch no longer exists, mark it `[stale]`. Report only — never delete.
3. **Follow pointers into memory** — read the verification-debt and pending-decisions files the handoff points at (`project_verification_debt.md`, `project_pending_decisions.md`), plus any others it names.
4. **Read other pointers only as needed** — do not pre-fetch every ADR / spec / ledger; that defeats the context-efficiency rationale. Read selectively, deeper reads after the user picks direction.
5. **Summarize** in a tight block (≤~15 lines): anchor (latest commit + branch state), one-line In-flight, one-line next move from START HERE, and *counts* (not contents) of verification-debt + pending-decision items.
6. **Wait for direction** — end with a one-line ready signal; do not start work. Non-negotiable.

**Anti-patterns.**
- Don't pre-fetch every pointer; read selectively.
- Don't start work after the summary — the user picks direction.
- Don't modify any handoff or memory file — read-only.
- Don't fire on ambient keywords — explicit `/resume` only.
- Don't check out the default branch to read the trunk kickoff from a feature branch — use `git show <default>:<path>`.
- Don't delete stale worktree handoffs — flag them; pruning is `handoff-kickoff`'s job on the trunk.
- Don't summarize the *contents* of verification debt or pending decisions — count them; the user reads the files if needed.

### Skill: `step-table` (global utility)

**Purpose.** The formatting authority for tables. Whenever output has parallel structure, present it as **one** markdown table rather than prose or a stacked list — this applies in every context (main session, subagents, other skills), not just step procedures. Carries (1) universal rules for every table and (2) column presets for common shapes; the presets are preferences, not fixed schemas.

**Trigger.** Content with parallel structure — the test is whether you'd otherwise repeat a lead-in phrase ("Step 1:", "Option 1:", "H1:", "Field:"). Not for a single one-off item with no parallel structure. Mirrors the tables-over-prose categories in root `CLAUDE.md` (§ Root `CLAUDE.md` shape → Agent operating notes).

**Universal rules (every table).**
- **Never let the table collapse** into a stacked "Field: value" list — that happens only when a cell holds an unbreakable token wider than the terminal (a long command or URL). Keep those out of cells: write `cmd ↓` / `link ↓` and put the full text in a fenced code block *beneath* the table.
- **No HTML in cells** (`<br>`, `<b>` render as literal text). A cell holds at most one sentence or one short command; anything multi-part goes below the table with a `↓` reference.
- **Cell budget ~12 words / ~80 chars.** Longer content moves below with a bold label (**Step 2 — …**).
- **Choose columns to fit the content** — carry only the columns that inform this content; drop the rest; don't pad empty cells.
- **One canonical table per thing.** On a mid-table question or progress update, answer first, then **re-print the entire table** with updated cells — never a partial slice.
- **Propagate to subagents explicitly** — paste the universal rules (and the relevant preset) into a subagent's prompt when its output will be shown to the user; skill content does not reach subagents on its own.

**Column presets (drop columns that don't apply; add ones the content needs).**
- **Step / procedure:** `#` · `Step` · `Action` · `Why` · `Performer` · `Status` · `Expected`, with an emoji legend above (`✅ done · 👉 now · ⬜ later` plus per-performer emoji). `Action` is the copy-pasteable command or exact click-path.
- **Results / summary:** `Field | Value` — one row per reported field.
- **Option comparison:** one row per option; columns are the dimensions traded off.
- **Status / hypothesis matrix:** one row per item under test; a `Status` column plus evidence columns.

**Anti-patterns.**
- Don't emit a stacked "Field: value" list where a table applies.
- Don't put HTML or multi-part content inside a cell — move it below with a `↓` reference.
- Don't re-print a partial table slice on an update — always re-show the whole table.
- Don't assume subagents inherit these rules — paste them into the subagent prompt.

## Handoff and kickoff

End-of-session handoff is the mechanism that prevents context rot across long-running projects. The lead agent generates a kickoff prompt; the next agent loads it as the entry point of the next session. Generator is the `handoff-kickoff` skill — output path resolution, behavior contract, kickoff section structure, and the required standing-instructions block all live in § Skills above.

**Why this section exists separately.** The skill describes *how to generate* the artifact; this section captures the *governance principles* the artifact serves. They're stable across skill rewrites.

**Single canonical file.** The kickoff is one file (`handoff-file:` directive, default `next-session-kickoff.md`), overwritten each regen — git history is the audit trail for prior snapshots. No dated filenames, no `-vN`. Kickoffs commit **and push** to `main` (`git push origin HEAD:main`, a normal fast-forward — never forced; a rejected push is reported, not forced past); from a phase branch, read the latest via `git show main:<path>`.

**Continuous-learning loop.** At the handoff boundary the generator first sweeps the session for its lessons — *corrections* (a wrong output the user fixed), *operational procedures* ("from now on…" rules), and *preferences* (format/tone/tooling) — and durably stores the approved ones before writing the kickoff, because session lessons evaporate otherwise. Each item is presented one at a time with concrete durable mechanisms as options (a memory file, a `CLAUDE.md` directive, a hook via `update-config`, or a skill edit); automated "whenever X" behaviors require a hook, since memory can't enforce them. De-dup against what's already stored so only genuinely new items surface. This is why the handoff skill's first step is interactive, not a mechanical write.

**Trunk vs branch handoffs.** `handoff-kickoff` captures the whole project and commits + pushes to `main`; `worktree-handoff` captures one feature branch as local-ephemeral scratch under the git common dir and **never commits or pushes** — that separation is what lets many worktrees wrap concurrently without contending for a ref. `resume` loads whichever matches the current branch (trunk kickoff on the default branch, the branch's worktree handoff on a feature branch). The trunk `handoff-kickoff` run also prunes worktree handoffs whose branch is gone; open work that outlives a branch is grafted into the trunk kickoff at that point.

**Regen at session boundary only.** Kickoffs regenerate when a session ends (user-signaled, or agent-proposed under context-budget pressure) — not on every mid-session state change. A mid-session closure that invalidates the active kickoff's "in-flight" or "open work" gets flagged in chat and reflected in memory; the active kickoff stays the snapshot it was, and the next boundary regen captures the new state.

**Narrative routing.** Verification debt and parked/waiting-on-human items do not live as inline kickoff tables — they live in memory (`project_verification_debt.md`, `project_pending_decisions.md`), and the kickoff emits one-line pointers. Both pass the persistence test (each entry eventually closes). Inline tables duplicated state that already had a home, drove same-day kickoff churn, and hid stale items behind a per-session snapshot.

**Kickoffs are historical artifacts; memory is the live view.** If a change invalidates a kickoff's "what landed" or "open work" sections, flag it to the user rather than silently editing the kickoff. Edit memory instead.

**Memory updates same turn as state changes.** When any tracked item changes state (a commit lands, a decision is made, an ADR is filed, an item is dropped or deferred), update the relevant memory file in the same turn. When an item fully closes, *delete* the entry — do not leave "done" markers; closed entries accumulate and obscure what is actually open.

**Standing-instructions block is non-negotiable.** Every generated kickoff must include the verbatim block from § Skills § handoff-kickoff. Stale memory leaks into next-session kickoffs and produces wrong premises — this is the rule that catches it.

## Bootstrap sequence

Concrete order to set up a fresh project from this document:

1. `git init` the project root. Create the directory skeleton (`docs/`, `docs/decisions/`).
2. Write the root `CLAUDE.md` per the shape section above. § Status reflects the current state ("Pre-implementation. Documentation scaffolding in place.").
3. Write `docs/CLAUDE.md` (path-scoped invariants for `docs/`): ADR shape, research-report frontmatter, in-repo plain-text pointers, no ephemeral artifacts.
4. Write `docs/canonical-sources.md` with the header (purpose, pointer-form conventions, registry instructions) and an empty registry table — first rows land as the first ADRs do.
5. Write `docs/polish-backlog.md` with usage instructions; empty initially.
6. First ADRs typically land here within the first session as foundational decisions accumulate. Candidates: roadmap-workflow ADR, polish-backlog ADR, context-budget ADR, any architecture decisions already made de facto.
7. Write `docs/roadmap.md` when the phase ordering is known. Phase 0 is the "Foundations" phase that captures the work of steps 1–6 plus first ADRs plus the roadmap itself. Phase 0 closes when the fresh-project setup instructions (this document) are written on a new project — making this document Phase 0's own exit artifact, recursively.
8. Initialize memory at `~/.claude/projects/<sanitized-project-path>/memory/MEMORY.md`. Empty index initially. First entry is usually a "pending decisions awaiting formalization" file holding decisions agreed in conversation that have not yet been codified.
9. Add path-scoped `CLAUDE.md` files for new top-level directories as they come online.
10. **Install skills.** Vendor the utility skills into the repo with `git subtree` (§ Skills → Vendoring the utility skills): `git subtree add --prefix=.claude/skills https://github.com/benhudelson/skills.git main --squash`. The shared upstream carries only the four utility skills (`handoff-kickoff`, `resume`, `worktree-handoff`, `step-table`), so the add needs no cleanup. The project-local workflow skills (`roadmap-phase-kickoff`, `publish-spec`) are authored per project at `<project-root>/.claude/skills/<name>/SKILL.md` from their § Skills contracts when their pipeline comes online, alongside the vendored utility skills. `handoff-kickoff` and `resume` are usable immediately (first `handoff-kickoff` invocation typically end-of-Phase-0 — its continuous-learning sweep runs from then on; `resume` at the next session start). `roadmap-phase-kickoff` first runs when the first feature phase opens. `/publish-spec` first runs when the first spec is ready to publish — at that point also file an ADR capturing any project-specific behavior or idempotency contract beyond what § Skills states.
11. **First feature → first spec** under `specs/YYYY-MM-DD-<feature-slug>/`. Author `specs/CLAUDE.md` (path-scoped) the same session. Before invoking `/publish-spec`, manually create the phase Initiative in the Linear UI (~30 seconds) — the skill aborts cleanly if it's missing.

**Initial canonical-sources rows.** Each foundational ADR adds a row. By end of Phase 0 the registry covers: roadmap workflow, polish backlog, roadmap content, context budget, attribution ban, and any architecture or product ADRs filed during foundations.

**Phase 0 exit gate.** Documentation scaffolding, ADRs, canonical-sources registry, workflow patterns, and these setup instructions all landed. Implementation begins in Phase 1.
